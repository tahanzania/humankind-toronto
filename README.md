# humanKIND toronto website

A static site: plain HTML, CSS and JavaScript, with no build step and no framework. The site files sit at the root of this repo, and Cloudflare Pages publishes the root as it is.

## Repo layout

```
.
├── index.html, about.html, … (14 pages, generated by tools/build.py)
├── _redirects             ← 301s from the old Squarespace URLs
├── _headers               ← caching and security headers
├── sitemap.xml, robots.txt, favicon.png
├── assets/
│   ├── css/styles.css
│   ├── js/main.js
│   └── img/               ← optimized WebP photos and logos
├── tools/
│   ├── build.py           ← generates the HTML pages (Python 3, no dependencies)
│   └── imgmeta.json       ← image width/height lookup used by build.py
├── README.md
├── .gitignore
└── docs/                  ← local only, not in git (see below)
```

> **Everything in this repo is published.** Cloudflare Pages serves every file at the root, so `tools/` and `README.md` are reachable on the live site (they're marked `noindex` in `_headers` so search engines skip them). Nothing private belongs in the repo. The client's copy document has internal editor comments (for example "SV: …"), so it is kept in a local `docs/` folder that `.gitignore` excludes. It still exists in the first commit's history, so keep the GitHub repo private.

The original full-resolution photos (about 161 MB) are not in the repo. Keep them in Drive or Dropbox. The `.gitignore` excludes the local `hK website photo options` folder so they can't be committed by accident.

## Deploy on Cloudflare Pages

1. In the Cloudflare dashboard go to **Workers & Pages → Create → Pages → Connect to Git**, and pick this repo.
2. Use these build settings:

   | Setting | Value |
   | --- | --- |
   | Production branch | `main` |
   | Framework preset | `None` |
   | Build command | *(leave empty)* |
   | Build output directory | `/` (the repo root) |

3. Click **Save and Deploy**. The site goes live at `https://<project-name>.pages.dev`. Every push to `main` redeploys it, and every other branch gets its own preview URL.

### Before you point the real domain at it

- Review the `.pages.dev` site first. The real domain still points at Squarespace until you change DNS.
- The canonical URLs, social-preview tags, `sitemap.xml` and structured data already use `https://www.humankindtoronto.org`, so they are correct for launch. On the `.pages.dev` preview they intentionally point at the final domain.
- To go live, add the domain under your Pages project's **Custom domains** tab and follow Cloudflare's DNS instructions. Do this only when you're ready to replace the Squarespace site.
- After launch, open each old address once to confirm it redirects: `/on-site`, `/fundraising`, `/create-for-a-cause-2026`, `/covid19-1`. Then submit `https://www.humankindtoronto.org/sitemap.xml` in Google Search Console.

### How the URLs work on Cloudflare Pages

Cloudflare serves `about.html` at `/about` and redirects `/about.html` to `/about`. Canonical tags and the sitemap use the clean URLs. Internal links keep `.html` so the site also works when you open the files straight from disk, at the cost of one quick redirect per click.

## Contact form

The form opens the visitor's own email app with the message filled in, addressed to helpforhumankind@gmail.com, so no server is needed. To receive submissions directly instead, point the form at a form service such as Formspree or Basin (the `contact-form` section of `tools/build.py`) and remove the `submit` handler at the bottom of `assets/js/main.js`. Cloudflare Pages has no built-in forms.

## Editing content

- **Page text, header, footer, navigation and SEO tags** live in `tools/build.py`. Edit that file, then regenerate:

  ```bash
  python3 tools/build.py
  ```

  This rewrites every `.html` page, `sitemap.xml`, `robots.txt` and `_redirects` in the repo root. **Don't hand-edit those generated files**, because the next run overwrites your changes. Commit both `tools/build.py` and the regenerated files, since Cloudflare publishes the repo root as it is and doesn't run the script.
- **CSS, JavaScript and images** aren't generated. Edit them directly in `assets/`.
- When you add a new photo that you reference through the script's `img()` helper, add its name and `[width, height]` to `tools/imgmeta.json`. Photos written directly into the page HTML in `build.py` don't need an entry.
- Photos are in `assets/img/` as WebP files, sized to 1400px on the longest edge. Always include descriptive `alt` text. If you replace an existing photo, give it a new filename, because images are cached for a year.
- Colours and fonts are CSS variables at the top of `assets/css/styles.css`.
- **After Nov 20, 2026:** update the event date (`EVENT_ISO` and `EVENT_HUMAN` at the top of `tools/build.py`) and the wording on the Create for a Cause page, the home page "Save the date" strip and the FAQ answer, then regenerate. The countdown hides itself once the date passes.

## SEO already in place

- Unique `<title>` and meta description on every page
- Canonical link, plus Open Graph and Twitter card tags
- Structured data (JSON-LD): NGO organization, WebSite, BreadcrumbList on inner pages, FAQPage and Event
- Semantic HTML landmarks, one `<h1>` per page, descriptive alt text
- `sitemap.xml` and `robots.txt`
- Lazy-loaded images with explicit dimensions, so the layout doesn't shift while images load
